# 中文书名全集的可行性调研

> 调研时间：2026-10（部分数据为最近可查口径）
> 结论先行：**没有人做成过「中国所有书的书名」，而且在可预见的将来也不会有开源项目做成。**
> 原因不是技术，而是书目数据的所有权结构。但「做到 90% 覆盖」是可行的，路径也清楚。

---

## 一、先把「所有书」这个词拆开

「中国所有书」至少是四个互相不同的问题，混在一起谈必然得出错误结论。

| 层 | 时间范围 | 权威口径的品种数 | 数据在哪 |
|---|---|---|---|
| 古籍 | 先秦—1911 | 《中国古籍总目》著录 **177,107 种**（经 15,144／史 66,502／子 38,298／集 54,889／丛 2,274）；含亡佚约 25.4 万种 | 国图、中华书局；《中国古籍总目》纸本+数据库 |
| 民国 | 1912—1949.9 | 《民国时期总书目》**12.4 万余种**；增补本约 20 万种；《民国时期图书总目》已出 10 卷 65,883 种，预计 20 余万种 | 国图民国文献保护计划 |
| 1949 后 | 1949.10— | 1949.10—1999.12 累计出版 **2,028,407 种**（其中新书 1,324,223 种）；此后每年 14—22 万种 | 中国版本图书馆（PDC） |
| 在售/可得 | 当下 | 当当图书 SKU 百万量级，京东、当当、孔夫子各成体系 | 商业电商 |

四个层的数量加起来是**千万量级**，其中绝大部分是 1949 年后的教材、教辅、年鉴、内部资料、
重印本。如果目标是「书名库」而非「出版史数据库」，必须先把边界定死，否则「不漏」无从验证。

### 一个绕不开的计数陷阱

「种」在中文出版语境里没有唯一定义。巴金《家》出过 26 个版本，算 1 种还是 26 种？
换出版社算不算新种？改名再版算不算？上海图书馆的普查把晚清至 1949 年的单行本统计为
「约 60 万种」，这个数字**包含了版本**，按「品种」算则远低于此。

**任何「中国共有 N 种书」的说法，都必须附带「种」的定义。** 本项目采用的定义是：

> 一种书 = 一个规范化书名（不含版本、卷册、副标题差异）。

按此定义，同一本书的不同版本合并为一条，书名相同但实质不同的书（如《大学》古籍本与现代
教材）视为不同条目 —— 这一点无法靠字符串完全区分，是本项目的已知误差来源。

## 二、有没有现成的东西可以直接用

有。但都要么太小，要么拿不到，要么不是「书名库」。

### 2.1 开源数据集（能直接下载的）

| 项目 | 规模 | 内容 | 可用性 |
|---|---|---|---|
| [JiangYanting/Chinese_book_dataset](https://github.com/JiangYanting/Chinese_book_dataset) | **13.3 万册** | 书名、作者、出版社、关键词、摘要、中图分类号、出版年月 | 需邮件/QQ 申请；学术用途 |
| [shjwudp/shu](https://github.com/shjwudp/shu) | 数百种 | **全文语料**，非书名库 | MIT，可直接用 |
| [豆瓣书评数据集](https://textdata.cn/blog/2024-04-17-douban-book-3394w-ratings-comments-dataset/) | 3,394 万条书评 / **17,967 部书** | 书评文本 + 书名 | 公开下载，但书只有 1.8 万部 |
| [HNGCL DoubanBook](https://deepwiki.com/zhangchi107/HNGCL/5.1-doubanbook-dataset) | **22,347 部** | 推荐系统用的交互图 | 学术数据集 |
| Open Library | 全球 2,000 万+ 条 | 含中文书，但中文覆盖稀薄、著录质量参差 | 免费 API，可整库下载 |

**判断**：这些加起来覆盖不到 20 万条，而且彼此高度重叠（都偏向畅销书与学术书）。
作为「冷启动词典」有价值 —— 本项目的书名切分词典正是这个用法 —— 但作为全集远不够。

### 2.1b GitHub 上的爬虫（可复用的只有单源脚本，没有成库）

我逐个搜了 `豆瓣图书 数据集 / douban book / ISBN 图书数据 / 国家图书馆 书目 /
图书馆 书目 爬虫 / 古籍 书目` 等关键词，结论一致：**GitHub 上没有现成的「中文书名库」，
只有若干针对单一站点的爬虫**，且规模都很小：

| 项目 | 说明 | 对我们的价值 |
|---|---|---|
| [baabaaox/ScrapyDouban](https://github.com/baabaaox/ScrapyDouban) ★788 | 豆瓣电影/读书 Scrapy 爬虫 | 可借鉴其反爬头与解析 |
| [stormstone/SpiderSSS](https://github.com/stormstone/SpiderSSS) ★83 | 豆瓣读书 + 当当爬虫笔记 | 印证了本项目的双源思路 |
| [FelixMundial/SimpleDoubanScraper](https://github.com/FelixMundial/SimpleDoubanScraper) | 豆瓣读书 API 化 | — |
| [GongDexing/douban-book-api](https://github.com/GongDexing/douban-book-api) | ISBN → 豆瓣数据查询 API | 可用于反查 ISBN |
| [dwj-cwq/spider-of-books](https://github.com/dwj-cwq/spider-of-books) | 豆瓣标签页爬虫 | 与本项目 douban 源同构 |
| [freestylefly/mcp-server-weread](https://github.com/freestylefly/mcp-server-weread) | 微信读书 MCP（需登录 cookie） | 佐证微信读书接口 |
| [JiangYanting/Chinese_book_dataset](https://github.com/JiangYanting/Chinese_book_dataset) | **13.3 万册**（唯一成规模数据集） | 需邮件申请，可作冷启动词典 |

**判断**：把这些加起来也拼不出一个书名库。它们解决的是「怎么爬某个站」，而本项目要解决的
是「爬来的东西怎么去重、怎么判质量、怎么回溯」——后者目前没有现成轮子。

### 2.2 权威数据源（数据最全，但不对个人开放批量）

**中国国家版本馆 PDC 平台（`pdc.capub.cn`）是唯一的「终局解法」。**

它是国家新闻出版署的出版物信息平台，后台汇聚近 2 亿条数据，对外开放检索 2,400 万余条：

| 库 | 时间范围 | 规模 |
|---|---|---|
| ISBN 数据库 | 2009— | **400 万条** |
| CIP 数据库 | 2000— | **500 万条** |
| 馆藏样本数据库 | 1949— | **650 万条** |

平台功能里明确包含「**批量套录**」：一次可提交 5,000 个 ISBN，命中后可按 Excel 或
CNMARC 下载。也就是说，只要拿到 ISBN 清单，650 万条馆藏样本数据是**可以工程量产**的。

障碍：接口需要登录态。我实测其前端 API（`POST /api/index/searchQuick`）在无账号时返回
`{"status":"failed","msg":"没有用户"}`。注册需要手机号，**这一步必须由你本人完成**，
我不能代你注册或持有账号。

同类但更难的：CALIS 联合目录（100 所高校馆藏）、国图 OPAC（`find.nlc.cn`，本环境不可达）、
WorldCat（API 需申请审批）、超星/读秀（商业授权）。

### 2.3 商业站点（可爬，但是「在售」而非「曾出版」）

| 站点 | 可枚举性 | 书名质量 | 备注 |
|---|---|---|---|
| 当当 | 分类树 674 个三级类目，逐层下钻 | 差（营销拼接） | 服务端渲染，著者/出版社结构化，**本项目主源** |
| 微信读书 | 分类树接口直接暴露 187 个叶子类目（合计约 97 万条），单类目可翻 500 条 | 好 | `GET /web/categories` + `bookListInCategory`，无需登录，**本项目第二主源** |
| 豆瓣 | 145 个标签 × 最多 1,000 条 | **最好** | 连续约 150 次请求后限流，需极慢速率 |
| 京东 | 搜索页触发人机验证 | — | 本环境不可用 |
| 孔夫子 | 前端渲染，需真实浏览器 | 好（含古籍、民国、绝版） | 覆盖旧书，是补 1949 前缺口的关键 |

**要害**：电商只卖**在售**的书。1949—2000 年间出版、如今绝版的几十万种书，电商页面上
根本不存在。这一块只能靠图书馆书目，不能靠爬虫。

## 三、所以「不重不漏」能做到什么程度

诚实的答案是分层承诺，而不是一句「我全做完了」。

| 目标 | 可行性 | 说明 |
|---|---|---|
| 在售中文图书书名，去重后 50 万+ | **可以做到** | 当当分类分层遍历；本项目已实现并跑通至 10 万+ 量级（实测见 `REPORT.md`） |
| 豆瓣已收录的 10 万级书名（高质量） | **可以做到，但需极慢速率** | 标签遍历，实测连续请求约 150 次后开始限流 |
| 1949 年以来正式出版物 ~500 万种 | **需要 PDC 账号** | 注册后批量套录，工程量产，非技术难题 |
| 民国图书 ~20 万种 | **需要图书馆书目** | 《民国时期图书总目》纸本 + 国图民国库 |
| 古籍 17.7 万种 | **需要《中国古籍总目》数据** | 有商业数据库（阅藏知津等），需授权 |
| 绝对意义的「一种不漏」 | **不可能** | 不存在完整的全国出版物清单；内部资料、非正式出版物从未被系统著录 |

### 一个必须说清楚的技术事实

「不重」和「不漏」在中文书名上是**互相冲突**的。举三个真实例子：

- 《红楼梦》 vs 《红楼梦（全二册）》 → 应合并（版本差异）
- 《西游记》 vs 《西游记续》 → 不应合并（不同书）
- 《大学》 vs 《大学·中庸》 → 边界模糊（合刊 vs 单行）

纯字符串算法无法区分这三种情况。因此本项目的设计是：**只对「规范化后完全一致」的书名
自动合并，近似但不相同的只输出候选清单供人工复核**（`data/review_near_duplicates.csv`）。
这条设计原则牺牲了一部分「不重」，换取了「不漏」的可控性 —— 对书名库来说，
误合并（把两本书并成一本）比漏合并（同一本书留两条）更难被发现、危害更大。

## 五、结论

1. **没有人做成过**。最大的开源中文书名数据集是 13.3 万册（还需申请），而权威口径的
   中文图书品种数是千万级。差距在两个数量级。
2. **做不成的原因不是算法**，是「全国出版物书目」这个数据本身不对外开放批量获取。
   PDC 已经是开放度最高的一个，仍需账号 + 人工导出。
3. **能做的部分很大**：在售图书 + 豆瓣长尾 + 古籍/民国专项，去重后做到 50—100 万条
   高质量书名是现实的。本项目在这条线上做到了工程可用。
4. **剩下的必须靠账号和授权**，不是靠更聪明的爬虫。这一点写在
   [`docs/ROADMAP.md`](./ROADMAP.md) 里，按你愿意投入的精力分了三档。
